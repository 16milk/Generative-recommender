# 生成式召回设计与算法梳理

> 本文基于四份内部设计/复盘文档，聚焦 **Generative Recall（生成式召回）** 的通用设计、核心算法与工程落地形态，抽象出可复用的方法论。

---

## 1. 生成式召回的两类形态

四份文档覆盖了两条主线：

1. **Semantic ID / Item Token 生成式召回**
   - 将推荐召回改写为：`用户行为序列 -> 生成下一个 item 的语义 ID / embedding -> 反查真实 item`。
   - 典型用于电商、内容推荐、音乐等推荐场景。
   - 核心是长序列建模、Tokenizer / SID 构建、NTP 生成任务、SID 倒排召回、在线低延迟解码。

2. **LLM 文本生成式召回**
   - 将内容理解型召回改写为：`内容/行为特征 -> LLM 生成 query / suggestion / intent -> 建库召回`。
   - 典型用于视频到 query（V2Q）、用户到 query（U2Q）、query 到 query（Q2Q）、看后搜推荐词等场景。
   - 核心是 Prompt / 蒸馏、触发生产、生成结果过滤、统一存储、近线建库、在线多路召回融合。

两类方法的共同点是：**不再只从已有候选池中打分，而是让模型直接生成召回线索**。区别在于：前者生成的是推荐系统内部的 item token / semantic id，后者生成的是可被搜索/召回链路使用的文本 query 或候选描述。

## 2. Semantic ID 生成式召回总体设计

### 2.1 离线与在线主链路

Semantic ID 类生成式召回可以抽象为以下闭环：

```text
离线侧：
  Item 多模态/召回 embedding
      -> Semantic ID / Tokenizer 构建
      -> SID 正排、倒排、SID->GID 映射
      -> 用户长序列样本生产
      -> 生成式模型训练
      -> 模型与静态缓存发布

在线侧：
  请求到达
      -> 读取用户序列/静态缓存
      -> 模型生成 U 侧候选 SID / item embedding
      -> SID 倒排或 ANN / HNSW 检索得到 GID list
      -> 与其他召回合并、去重、过滤
      -> 进入粗排/精排/混排
```

核心设计目标：

- **用生成模型直接表达用户下一步兴趣**，而不是只学习 `u * i` 判别式打分。
- **用分层 SID 压缩海量 item 空间**，避免在十亿级 item 上做完整 softmax。
- **用倒排或 ANN 将生成结果还原为真实 item 候选**，接入现有排序链路。
- **保留现有召回通路并新增一路 GR**，便于 AB、回滚和收益归因。

### 2.2 SID / Tokenizer 设计

推荐场景中的 item 规模远大于 NLP 词表，因此 Tokenizer 是生成式召回的基础模块。文档中涉及的主流方案包括：

| 方案 | 核心思想 | 优点 | 风险 |
|---|---|---|---|
| Residual Quantization / RQ-VAE | 用多层 codebook 逐步量化 item embedding 残差 | 可学习，表达能力强 | 容易出现 codebook 倾斜，少数 token 被大量 item 命中 |
| 层次 K-means | 对 embedding 做多层聚类，生成分层 code | 分桶相对均匀，工程简单 | 聚类不可端到端学习，表达受 embedding 质量限制 |
| Balanced RQ-KMeans | 混合 RQ 与 K-means，并显式约束分桶均衡 | 兼顾语义与均衡性，适合工业倒排 | 生产链路和评估更复杂 |
| 无 Tokenizer / HNSW | 模型直接生成 item embedding，再用 ANN 检索 item | 不依赖 SID 词表，接入现有向量检索方便 | 更像生成 embedding + I2I 检索，难以完全摆脱 ANN |

推荐的第一阶段做法：

1. 使用多模态 embedding 或推荐召回 embedding 作为 item 表征来源。
2. 采用 **balanced hierarchical tokenizer**，生成 2~4 层 SID，例如 `(sid_1, sid_2, sid_3)`。
3. 建设 `item -> SID` 正排和 `SID prefix/full path -> item list` 倒排。
4. 对 SID 做以下质量评估：
   - 每层 token 分布均匀度。
   - full path collision 情况。
   - 每个 SID 桶平均 item 数。
   - 新 item / 变更 item 的 SID 稳定性。
   - 在线 SID 命中率与倒排可召回率。

### 2.3 SID 构建与更新策略

SID 的 embedding 来源会影响稳定性：

- **只用多模态 embedding**：语义稳定，适合 T+1 / T+2 批式更新；对推荐行为变化不够敏感。
- **拼接召回 embedding**：更贴近业务召回空间；但 item SID 会更频繁变化，导致样本特征不一致、模型追新难度增大、倒排过期处理复杂。

因此工程上需要配套：

1. **版本化 SID**：SID 生产、样本训练、倒排写入都带版本，保证训练/serving 一致。
2. **旧 SID 过期机制**：当正排中 item SID 变化时，倒排侧要删除或过期旧 SID 下的 item。
3. **增量与全量结合**：高时效业务可增量更新，新歌/新商品等低时效阶段可先 T+1 批式。
4. **序列 SID 回溯**：用户历史序列中落的是当时的 SID 还是最新 SID，需要明确；否则训练和在线特征会错位。

## 3. 模型架构与训练算法

### 3.1 Encoder-Decoder 主方案

四份文档中最完整的推荐类 GR 方案采用 Encoder-Decoder：

```text
用户长行为序列 X
  -> 静态历史 X_s：天/周级，离线编码并缓存
  -> 动态历史 X_d：分钟/小时级，在线实时编码或解码前缀

Encoder:
  H_s = Enc(X_s)
  H_d = Enc(X_d)
  H = [H_s; H_d]

Decoder:
  以 <bos>、<action>、已生成 SID token 为前缀
  自回归生成下一个 item 的 SID token 序列
```

这种方案的优点：

- 静态长历史可以离线编码，在线只处理短动态段。
- Encoder 可做更复杂的历史理解，Decoder 负责生成。
- Cross-attention 可让生成过程读取完整用户历史记忆。
- 相比 decoder-only，长序列前缀构建成本更可控。

### 3.2 输入 token 组织

典型 token 组成：

```text
<bos>
<action=impr|click|cart|order>
<sid_l1> <sid_l2> <sid_l3>
<time_bucket(delta_t)>
<session_sep>
...
<eos>
```

关键设计：

- **item token**：由 SID 多层 code 组成。
- **action token**：区分点击、加购、下单、播放等行为。
- **time bucket**：表达相邻行为时间差、行为距请求时间的间隔。
- **session separator**：帮助模型区分会话边界。
- **控制 token**：如 `<action=click>`、`<action=order>`，用于指定生成目标。

### 3.3 样本组织：长序列 + 当前 session

推荐类生成式召回的训练样本通常采用：

```text
Encoder 输入：用户历史行为序列 / 静态长历史
Decoder 输入：当前 session 前缀或目标 action prompt
Decoder 目标：当前 session 内 item SID，或下一次交互 item SID
```

电商长序列方案中，序列长度可达到 4K 级别：

- 多条原始序列（曝光、点击、加购、成交）先 merge。
- 按时间升序排序。
- 按 `(item, timestamp)` 或 `(item, action)` 去重。
- 过滤目标 action。
- 补充 side info 与时间分桶。
- 截断/填充到固定长度。

这种 listwise / long sequence 组织方式比 pointwise 样本更贴近生成式建模，也能补充全网成交等稀疏行为信息。

### 3.4 生成式任务：Next Token Prediction

基础训练目标是自回归预测目标 item 的 SID 序列：

$$
\mathcal{L}_{gen}
= - \sum_{t=1}^{m} \log p_\theta(y_t \mid y_{1:t-1}, H, c)
$$

其中：

- $H$ 是 Encoder 输出的用户历史记忆。
- $c$ 是控制 token，例如目标 action。
- $y_t$ 是目标 item SID 的第 $t$ 层 token。

推理时用 beam search / top-k / constrained decoding 生成多条 SID path，再通过倒排召回真实 item。

### 3.5 判别式辅助任务：Batch Softmax / InfoNCE

仅做 NTP 会学到“可能生成什么”，但召回还需要区分目标 item 与负样本。因此文档中设计了判别式辅助目标：

1. 对真实 item 和采样 item 分别计算其 SID 序列在生成头上的自回归 log-likelihood。
2. 将序列 token 概率累加为候选 item 分数：

$$
s_{n,j}=\sum_{t=1}^{m}\log p_\theta(y_{j,t}\mid y_{j,1:t-1},H_n,c)
$$

3. 在 in-batch negatives / 难负样集合上做 batch-softmax：

$$
\mathcal{L}_{disc}
= -\sum_n \log \frac{\exp(s_{n,j^*}/\tau)}
{\sum_{j\in \mathcal{C}_n}\exp(s_{n,j}/\tau)}
$$

总损失可写为：

$$
\mathcal{L}
= \lambda_{gen}\mathcal{L}_{gen}
+ \lambda_c\mathcal{L}_{disc}^{click}
+ \lambda_o\mathcal{L}_{disc}^{order}
$$

这种设计的价值：

- 复用生成式 softmax 头，不额外引入完全独立的双塔头。
- 让生成概率和候选区分能力对齐。
- 可针对 click/order 等不同行为分别训练。

### 3.6 偏好对齐：DPO / Reward / GRPO

生成式召回的后续优化可以引入用户反馈对齐。文档中讨论了三类方案：

| 方案 | 数据来源 | 优点 | 风险 | 适合阶段 |
|---|---|---|---|---|
| 离线 DPO | 从已有曝光/候选中构造高低 reward session pair | 工程简单，反馈真实 | off-policy，采样偏差大 | 早期探索 |
| 模型内 Reward Tower | 在 Encoder 基础上增加 XTR tower，对 rollout item/session 打分 | on-policy，速度快 | reward 输入特征较弱，准确性有限 | 中期 |
| 线上精排打分 Reward | GR rollout 后调用现有精排模型打分 | reward 质量高，贴近业务目标 | 链路复杂，训练成本高 | 后期 |

推荐演进路线：

1. 先用 NTP + 判别式辅助任务跑通召回闭环。
2. 再尝试模型内 reward tower + DPO。
3. 最后在 ROI 明确后接入精排 reward，探索 GRPO / PPO 等 on-policy 优化。

## 4. 在线推理与召回服务设计

### 4.1 在线通路

Semantic ID 生成式召回的在线通路可以抽象为：

```text
请求
  -> 并行获取用户特征 / GR 所需序列特征
  -> GR provider 调模型生成 beam_paths / scores
  -> recall node 用 SID 查询倒排
  -> 得到 GID candidates
  -> post-process：去重、截断、过滤、打分透传
  -> 与其他召回合并
```

关键工程取舍：

- **模型推理前置并与用户特征节点并行**，降低串行访问带来的延迟。
- **把 SID 作为 U 侧生成特征或 provider 输出**，下游 recall node 只负责倒排召回。
- **beam_paths 与 beam_scores 均透传**，便于倒排结果加权、merge 和后续排序使用。

### 4.2 Cache 设计

长序列 GR 的在线成本主要来自两部分：

1. 静态长历史编码。
2. 自回归生成时的 KV cache。

可采用：

- **静态历史缓存**：离线小时级更新 `H_s = Enc(X_s)`。
- **动态历史在线计算**：在线只处理最近 session 或近 2 小时行为。
- **Decoder KV-cache**：beam search 共享 prefix cache，分叉部分各自维护。
- **时间游标去重**：离线更新后，已进入 `H_s` 的动态 token 要从在线 KV-cache 中清理。
- **量化压缩**：Encoder memory 可用 BF16/FP8/INT8；KV-cache 可用 8/16 bit。

### 4.3 SID 倒排召回

倒排 key 可以是：

```text
sid_l1_sid_l2_sid_l3
```

value 是该 SID path 下的 item / gid list。

常见召回策略：

- full SID path 精确召回。
- prefix SID path 兜底召回。
- beam path 多路召回后按 beam score 加权。
- 对 SID 桶过大时截断或采样。
- 对 SID 桶过小时用父层 SID、ANN 或热门 item 补充。

## 5. LLM 文本生成式召回设计

LLM 生成式召回与 SID GR 的目标不同：它不是直接生成 item SID，而是生成可被搜索/推荐系统使用的 query、suggestion、标签或意图候选。

### 5.1 统一生成层架构

LLM 生成式召回可拆成三层：

```text
生成层：
  trigger -> 过滤 -> 特征获取 -> 调用 LLM / relevance_predict -> 生成结果

近线层：
  读取生成结果 -> 建库 / 写索引 / 写正排 -> 触发召回数据更新

在线层：
  请求 -> 读取生成召回结果 -> 多路召回融合 -> 排序/过滤/退场
```

统一架构的关键抽象：

- 生成层按 `video / user / query` 三类对象抽象，支持 V2Q、U2Q、Q2Q。
- 触发任务只负责聚合、过滤和传字段，不感知具体业务生成频道。
- 生成结果使用统一结构存储，包括 query、gid、suggestions、trigger_source、score、extra 等。
- 通过请求版本和数据版本支持模型迭代、trigger 替换、灰度与 AB。
- 统一打点：过滤率、生成有结果率、写存储成功率、近线/在线漏斗。

### 5.2 看后搜 LLM 召回算法

看后搜推荐词场景的生成式召回核心是：

```text
视频内容特征 + 用户后验行为
  -> LLM 判断是否适合推荐 query
  -> 筛选可参考的用户看后搜 query
  -> 生成高质量、多样化推荐词
  -> 过滤、持久化、近线建库
```

输入特征包括：

- 视频标题、类目、摘要、作者、BGM、IP 名称等内容特征。
- 用户看后搜 query 队列、热门评论等行为特征。

算法设计重点：

1. **Task Planning Prompt**
   - 将任务拆成：理解视频内容、判断推荐价值、筛选用户 query、生成推荐词。
   - 让 Teacher 模型输出思维链、推荐价值、参考 query、生成 query。

2. **黑箱上下文蒸馏 BICD**
   - 使用大模型 Teacher 生成 `CoT + Answer` 小规模高质量训练集。
   - 用轻量 Student 模型学习两类数据：
     - 完整上下文：`Task Planning Prompt + 输入 -> CoT + Answer`。
     - 精简上下文：`Slim Prompt + 输入 -> Answer`。
   - 通过混合 SFT 将 Teacher 的任务规划、指令遵循和生成能力蒸馏到 Student。

3. **线上高效推理**
   - 线上只使用精简 Student Prompt。
   - 生成后做规则过滤、名单质量控制和近线建库。

4. **质量保障**
   - 生成结果参与现有召回、排序和退场机制。
   - 对高展 query 触发复审，控制安全性和承接质量。

### 5.3 触发策略与成本收益

LLM 生成召回通常不适合对全量对象实时生成，需要事件触发：

- 按 VV / 曝光 Counter 多档阈值触发。
- 对内容正排、评论、用户行为发生变化的对象重新生成。
- 对历史 hot 对象旁路刷入，加速新版本覆盖。

多档触发的价值：

- 控制推理 QPS 和成本。
- 在内容生命周期不同阶段使用不同置信度的特征。
- 兼顾冷启动覆盖和高价值对象质量。

## 6. 两类生成式召回的对比

| 维度 | SID / Item Token GR | LLM 文本 GR |
|---|---|---|
| 生成目标 | item SID、item embedding、session item list | query、suggestion、搜索意图 |
| 输入 | 用户行为长序列、action、time bucket、item side info | 内容特征、评论、后验搜索行为、上下文 prompt |
| 训练目标 | NTP、batch-softmax、DPO/GRPO | Prompt distillation、SFT、规则/人工反馈优化 |
| 检索方式 | SID 倒排、ANN/HNSW、SID->GID map | query 建库、文本索引、现有召回结果读取 |
| 主要价值 | 学习用户兴趣迁移，扩展推荐候选空间 | 提升中长尾/冷启内容覆盖，提供原创高质量 query |
| 主要风险 | SID 稳定性、长序列成本、beam 延迟、空召回 | 幻觉、落地页承接、质量审核、生成成本 |
| 落地方式 | 新增一路 GR recall 接入排序 | 新增一路 LLM recall 参与多路召回 |

## 7. 推荐的落地路线

### 7.1 P0：最小可用闭环

1. 选择稳定 item embedding，构建 3 层左右 SID。
2. 建设 SID 正排、倒排和 SID->GID map。
3. 生产用户行为序列样本，先覆盖 click/order 等核心 action。
4. 训练 Encoder-Decoder NTP baseline。
5. 离线评估 HR@K、MRR、SID 命中率、倒排空结果率。

### 7.2 P1：在线召回实验

1. 在线 provider 生成 beam SID path。
2. recall node 用 SID 倒排召回 gid list。
3. 与现有召回 merge，按 beam score、SID 层级、桶大小做加权。
4. 配置化控制召回量、超时、降级和 AB。
5. 建设监控：延迟、空召回、生成 path 分布、倒排桶大小、在线占比、下游点击/转化。

### 7.3 P2：长序列与多任务增强

1. 引入 4K 级 long sequence，区分静态历史和动态 session。
2. 上线静态 Encoder memory cache 与 Decoder KV-cache。
3. 加入 batch-softmax / InfoNCE 判别式辅助任务。
4. 对 click/order/cart 等目标做多任务训练。
5. 评估不同 Tokenizer、序列长度、beam size、cache 命中率对效果和延迟的影响。

### 7.4 P3：偏好对齐与统一推荐

1. 用真实曝光反馈构造 DPO pair。
2. 尝试模型内 reward tower，降低 on-policy 成本。
3. ROI 明确后接入精排 reward，探索 GRPO/PPO。
4. 从“生成一路召回”逐步扩展到 listwise generation、召回排序一体化。

## 8. 关键风险与检查清单

### 8.1 算法风险

- SID 分桶不均，导致部分 token 学不到或倒排过大。
- SID 频繁变化，造成训练样本和在线 serving 不一致。
- NTP 只学习共现，不足以优化业务偏好。
- Beam path 多样性不足，候选集中在少数 SID 桶。
- 生成式召回扩覆盖后，CTR 短期可能下降，需要排序和退场机制配合。

### 8.2 工程风险

- GR 推理与倒排串行导致延迟增加。
- 长序列 cache 存储成本过高。
- 动态历史与静态缓存边界不清，导致重复编码或漏行为。
- 倒排更新不及时，旧 SID 未过期。
- 生成结果缺乏版本控制，AB 与回滚困难。

### 8.3 观测指标

| 模块 | 指标 |
|---|---|
| SID | token 分布、collision、桶大小、SID 变更率、倒排覆盖率 |
| 模型 | NTP loss、disc loss、HR@K、MRR、beam path 多样性 |
| Serving | 模型耗时、倒排耗时、cache 命中率、空召回率、降级率 |
| 在线 | GR 占比、独占点击、点击/转化、下游排序通过率、退场率 |
| LLM GR | 触发量、生成有结果率、过滤率、人工准确率、落地页承接率 |

---

## 9. 总结

生成式召回可以统一理解为：**把召回线索从“检索已有候选”升级为“模型生成候选表达”**。

- 对推荐类 GR，核心是 `用户长序列 -> SID / item token -> 倒排召回`，重点在 Tokenizer、长序列建模、NTP + 判别式 loss、低延迟 serving。
- 对 LLM 类 GR，核心是 `内容/行为上下文 -> query / suggestion -> 近线建库`，重点在 Prompt 规划、上下文蒸馏、触发生产、质量过滤和统一架构。

短期最稳妥的落地方式是：**在现有推荐链路中新增一路生成式召回，先跑通 SID / query 生成、倒排/建库、在线 AB 与监控闭环；中期再引入长序列缓存、多任务判别式 loss、DPO/GRPO；长期探索召回、排序、重排统一的生成式推荐架构。**
