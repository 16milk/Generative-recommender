## 1. 为什么需要"生成式推荐"

过去十余年，工业推荐系统的主流是 **深度学习推荐模型（DLRM, Deep Learning Recommendation Model）**，典型代表是 Wide&Deep、DeepFM、DIN、DIEN 等。它们的共同点是：

- 把推荐建模成一个 **判别式（discriminative）** 任务：给定 `<用户, 物品, 上下文>`，预测点击率（CTR）、转化率（CVR）等 `pAction`。
- 依赖海量 **高基数、异构的稀疏特征**（用户 ID、物品 ID、各类交叉特征），靠特征工程驱动效果。
- 采用 **多级级联（cascade）** 架构：召回（retrieval）→ 粗排 → 精排 → 重排，每一级独立优化。

这套范式遇到了两个根本瓶颈：

1. **算力无法换效果（不 scale）**：与 LLM 不同，传统 DLRM 在堆参数、堆算力时收益很快饱和，难以观察到清晰的 Scaling Law。
2. **级联架构的天花板**：每一级的目标各自独立，上一级的结果成为下一级的"上界"，信息在级联中被层层裁剪，全局最优难以达成。

而大语言模型（LLM）证明了一件事：**当把任务统一成"序列上的下一个 token 预测"，并配合 Transformer + 大规模数据 + 大算力时，能力会随算力呈幂律增长（Scaling Law）。**

生成式推荐正是把这一思路迁移到推荐：**把用户行为序列当作"语言"，把推荐重新表述为一个自回归的序列生成问题。** Meta 在 2024 年的论文标题精炼地概括了这一点——*"Actions Speak Louder than Words"（行为比文字更响亮）*：用户的行为（actions）就是推荐领域的"token"，是一种被长期低估的、可用于生成式建模的模态。

## 2. 背景知识：从判别式到生成式

### 2.1 判别式推荐（传统范式）

```
输入: [用户特征] + [候选物品特征] + [上下文]
模型: DLRM / DIN / 双塔
输出: P(click | user, item) —— 一个标量分数
流程: 召回 → 粗排 → 精排 → 重排（多级独立模型）
```

特点：需要为每个候选物品打分，因此召回阶段必须先用近似最近邻（ANN）等手段把候选集从亿级缩到千级。

### 2.2 序列推荐（过渡阶段）

GRU4Rec、Caser、**SASRec**、BERT4Rec 等模型开始把用户历史看成序列，用 RNN/Transformer 编码序列、预测"下一个交互物品"。这是从判别式走向生成式的关键过渡：
- SASRec：用单向（causal）自注意力做 next-item 预测。
- BERT4Rec：用双向 Masked LM 思路。

但这一代模型规模仍小，且通常只用于召回，没有统一召回与排序，也没有展现出明确的 Scaling Law。

### 2.3 生成式推荐（当前范式）

核心转变：**不再为每个候选物品单独打分，而是让模型直接"生成"下一个（或下一组）物品的标识符。**

```
输入: 用户的历史行为序列（item / action 交织的 token 序列）
模型: 自回归 Transformer（或其变体 HSTU、Lazy Decoder 等）
输出: 自回归地生成下一个物品的标识符（Item ID 或 Semantic ID）
流程: 用一个统一的生成模型同时承担召回与排序
```

这与 GPT 生成下一个词完全同构——只是"词表"从自然语言词，换成了 **物品标识符 / 用户行为**。

## 3. 核心思想与范式转变

| 维度 | 判别式 DLRM | 生成式推荐 GR |
|------|-------------|---------------|
| 任务形式 | 预测 `pAction`（打分） | 自回归生成下一个物品标识符 |
| 建模对象 | `<user, item>` 特征交叉 | 用户行为序列（time series） |
| 训练目标 | 二分类 / 回归损失 | Next-token 预测（交叉熵） |
| 架构 | 多级级联，多个独立模型 | 单一生成模型统一召回+排序 |
| 候选生成 | ANN 召回 + 逐个打分 | Beam Search 解码直接生成 |
| Scaling | 很快饱和 | 呈幂律（power-law）增长 |
| 推理 | 对每个候选打分 | 解码生成 + 微批摊销（M-FALCON） |

范式转变带来三个直接收益：

1. **统一架构**：召回、排序甚至重排可以用同一个模型完成，减少级联误差累积。
2. **可 scale**：首次在十亿级用户的工业系统中观察到推荐模型的 Scaling Law（Meta HSTU），意味着"加算力就能涨指标"。
3. **更强的序列与语义建模**：长序列、多模态语义被统一进 token 空间。

## 4. 关键技术拆解

搭建一套生成式推荐系统，需要解决以下几个核心子问题。

### 4.1 物品标识符（Item Tokenization）

这是 GR 区别于 LLM 的最关键设计：**如何把一个物品变成模型可以"生成"的 token？**

主要有两条路线：

#### (a) 直接预测原始 Item ID
代表：Netflix Foundation Model、Pinterest PinFM。
- 适用于 **物品目录相对稳定** 的场景。
- 缺点：物品基数巨大（亿级），冷启动物品没有充分训练，词表稀疏。

#### (b) 语义 ID（Semantic ID）—— 当前主流
代表：Google **TIGER**、快手 **OneRec**、Spotify 等。

核心思想：先把物品 embedding 量化（quantize）成 **一组分层的离散 token**，相似物品共享前缀 token，从而获得泛化能力并大幅压缩词表。

常见量化方法：
- **RQ-VAE（Residual-Quantized VAE）**：TIGER 提出，用残差量化自编码器把 embedding 编码成多层 codeword。
- **RQ-Kmeans（残差量化 K-means）**：快手 OneRec 提出，将协同信号融入语义 ID，并最大化 codebook 利用率。

示例（OneRec 的做法）：
```
物品 embedding → 3 层 RQ-Kmeans（k=8192）
→ 得到 3 个 codebook 索引，如 [301, 99, 7011]
→ 语义 ID = 301-99-7011
→ 3 层 × 8192 ≈ 5000 亿 个可能的语义 ID，足够覆盖现代推荐目录
```

语义 ID 的好处：
- **泛化**：相似物品共享前缀 token，缓解冷启动。
- **压缩词表**：从亿级 Item ID 压到几千级 codebook。
- **分层 coarse-to-fine**：解码时从粗到细，可配合 Beam Search。

> 一个关键发现（Spotify 2025）：语义 ID 的质量强依赖底层 embedding 空间——为搜索微调的 embedding 利于搜索，为推荐微调的利于推荐；通过多任务联合训练的 bi-encoder 可以得到搜索/推荐兼顾的语义 ID。

### 4.2 序列构造（Sequence Formulation）

把用户历史组织成 token 序列。Meta HSTU 的做法是把 **物品（item）与行为（action）交织** 成统一的时间序列，并把其他类别特征编码为"缓慢变化的时间序列"。OneRec 则会编码多路用户序列（如短期/长期/正反馈/特定场景）。

### 4.3 主干网络（Backbone）

- **HSTU（Hierarchical Sequential Transduction Unit）**：Meta 提出的因果自回归 Transformer 变体。针对推荐的高基数、非平稳流式数据，用 **pointwise aggregated attention** 替代标准 softmax 注意力，在 8192 长序列上比 FlashAttention2 的 Transformer 快 5.3×–15.2×。
- **Encoder-Decoder（T5 风格）**：OneRec-V1 采用，用 encoder 编码多路用户序列，decoder 自回归生成目标物品的语义 ID。FFN 常用 **MoE（混合专家）** 以低成本扩大参数。
- **Lazy Decoder-Only**：OneRec-V2 提出的精简 decoder-only 架构，去掉 encoder、简化 cross-attention（去掉 K/V 投影层），算力需求降低 94%、训练资源降低 90%，在同等算力下支持 16× 更大的模型（0.5B → 8B）。

### 4.4 训练目标与对齐

- **预训练**：Next-token 预测 + 交叉熵损失（与 LLM 一致）。
- **后训练 / 偏好对齐**：OneRec 引入 **DPO（Direct Preference Optimization）** 做偏好对齐，以在多个相互冲突的业务目标（如时长、互动、留存）之间做权衡——这与 LLM 的 RLHF/DPO 思路一脉相承。
- **List-wise 生成**：OneRec 的 session-wise list generation 直接生成一组相互依赖的视频列表，而非孤立的单个物品。

### 4.5 推理与工程

- **Beam Search 解码**：分层生成语义 ID，天然支持多样性。
- **M-FALCON**：Meta 提出的推理算法，通过微批（micro-batching）+ 缓存摊销算力，可在相同推理预算下服务 285× 更复杂的模型。
- **流式更新**：推荐数据非平稳、物品目录快速变化（尤其短视频），需要持续/增量训练。

## 5. 涉及的技术栈

下面是从零搭建一套生成式推荐系统会用到的技术栈，按层次组织。

### 5.1 算法 / 建模层
- **序列建模**：Transformer、causal attention、HSTU、SASRec（baseline）。
- **量化 / Tokenization**：RQ-VAE、RQ-Kmeans、VQ-VAE、Product Quantization。
- **表示学习**：双塔/bi-encoder、对比学习（contrastive learning）生成物品 embedding。
- **大模型技巧**：MoE、GQA（Grouped Query Attention）、KV Cache、RoPE 位置编码。
- **对齐**：DPO、RLHF、reward modeling。

### 5.2 框架 / 库
- **深度学习框架**：PyTorch（主流）、JAX（部分研究）。
- **分布式训练**：DeepSpeed、Megatron-LM、FSDP、Ray。
- **高性能算子**：FlashAttention / FlashAttention2、Triton、CUDA。
- **开源参考实现**：[`meta-recsys/generative-recommenders`](https://github.com/meta-recsys/generative-recommenders)（HSTU 官方代码）。
- **召回/向量检索**：FAISS、ScaNN（用于 baseline 或混合架构）。

### 5.3 数据 / 特征层
- **特征存储**：Feature Store（如 Feast）。
- **流处理**：Kafka、Flink（处理实时行为流）。
- **数仓/湖**：Spark、Iceberg / Hudi、HDFS / 对象存储。
- **公开数据集（做实验）**：MovieLens-25M、Amazon Reviews、KuaiRand 等。

### 5.4 服务 / 工程层
- **在线推理**：TensorRT、ONNX Runtime、vLLM 思路的 KV-cache 服务、微批（M-FALCON 思想）。
- **AB 实验平台**：用于线上指标验证（CTR、时长、留存）。
- **监控**：模型/特征漂移监控、在线离线一致性。

### 5.5 评估指标
- **离线**：HR@K（Hit Rate）、NDCG@K、Recall@K。
- **在线**：CTR、人均时长、留存、GMV 等业务指标 + AB 测试。

## 6. 前沿进展（2024–2026）

生成式推荐被许多人称为"推荐系统的 ChatGPT 时刻"。主要里程碑：

### 6.1 Google TIGER（2023）
《Recommender Systems with Generative Retrieval》。首次系统性提出用 **RQ-VAE 生成 Semantic ID** + 自回归生成做 **生成式召回（generative retrieval）**。奠定了"语义 ID"这一关键组件，但仅用于召回。

### 6.2 Meta HSTU（ICML 2024）
《Actions Speak Louder than Words: Trillion-Parameter Sequential Transducers for Generative Recommendations》。
- 把召回与排序 **统一** 为序列转导任务。
- 提出 HSTU 架构 + M-FALCON 推理算法。
- 在公开数据集上 NDCG 最高提升 65.8%，比 FA2 Transformer 快 5.3–15.2×。
- **1.5 万亿参数** 的 GR 在线上 AB 测试提升 12.4%，部署于十亿用户平台。
- **首次在工业级推荐系统中观察到 Scaling Law**（跨三个数量级，达到 GPT-3/LLaMA-2 算力规模）。
- 这被广泛认为是 GR 范式真正"出圈"的转折点。

### 6.3 快手 OneRec（2025）
《OneRec: Unifying Retrieve and Rank with Generative Recommender and Preference Alignment》。
- T5 风格 encoder-decoder + MoE。
- 自研 **RQ-Kmeans** 把协同信号融入语义 ID。
- **Session-wise list generation**：直接生成相互依赖的视频列表。
- **DPO 偏好对齐**：在冲突业务目标间权衡。
- 是工业界 **直接生成物品 ID 的生产级系统** 的代表之一。

### 6.4 OneRec-V2（2025）
- 提出 **Lazy Decoder-Only 架构**：去掉 encoder、简化 cross-attention，算力降 94%，模型规模从 0.5B 扩到 8B。
- 把用户上下文当作静态表示，把算力集中到 decoder 上，使 decoder-only 在工业规模上变得实用高效。

### 6.5 其他厂商的探索
- **Netflix Foundation Model**：生成式推荐基础模型，直接预测 Item ID。
- **Pinterest PinFM**：直接预测 Item ID。
- **小红书 RankGPT**：偏向预测下一个物品上的行为集合。
- 多家互联网团队均在投入 GR 范式。

### 6.6 语义 ID 的精细化（Spotify 2025）
研究表明语义 ID 的构造方式至关重要：任务专用 ID 在单任务上强但难泛化；通过多任务联合训练的 bi-encoder 得到的 **跨任务语义 ID** 能在搜索与推荐间取得平衡，且无额外成本——指向更通用的生成式推荐基础模型。

## 8. 挑战与开放问题

1. **物品 Tokenization 的稳定性**：短视频等场景物品快速诞生/消亡，语义 ID 的 codebook 需要持续更新，又要保持训练-服务一致性。
2. **冷启动**：语义 ID 缓解但未完全解决；新物品/新用户仍需特殊处理。
3. **多目标权衡**：时长、互动、留存、商业化常常冲突，DPO/多目标对齐仍是开放课题。
4. **推理成本**：生成式 + Beam Search 比单纯打分更贵，需要 M-FALCON、KV-cache、量化等工程手段摊销。
5. **实时性与非平稳性**：推荐数据是流式、非平稳的，增量/持续学习比 LLM 更关键。
6. **评估鸿沟**：离线指标（NDCG/HR）与线上业务指标未必一致，最终仍需 AB 测试。
7. **多样性与同质化**：自回归生成可能放大热门偏置，需要显式控制多样性与探索。
8. **可解释性与合规**：生成式黑盒在可解释、公平性、内容安全方面带来新挑战。

## 9. 未来展望

1. **推荐基础模型（RecSys Foundation Models）**：像 LLM 一样，出现可跨域、跨任务复用的推荐基础模型，统一搜索、推荐、广告。Scaling Law 的确立让"预训练一个大模型 + 下游微调"成为可能。
2. **搜索 + 推荐 + 广告统一**：用同一套生成式框架与共享语义 ID 服务多个业务（Spotify 的跨任务语义 ID 是早期证据）。
3. **多模态原生**：物品的文本、图像、视频、音频信息直接进入语义 ID 与生成过程，实现真正的多模态推荐。
4. **LLM 与推荐深度融合**：用户可用自然语言表达意图，推荐与对话/Agent 结合，走向"可对话、可解释、可编辑"的推荐。
5. **算力换效果常态化**：随着 Scaling Law 被广泛验证，推荐进入"堆算力即涨指标"的阶段，模型规模持续上探（已从亿级走向万亿级）。
6. **架构进一步精简与高效**：Lazy Decoder、MoE、线性注意力等让大模型在严苛的推荐延迟预算内可服务。
7. **更强的对齐与控制**：从单一 CTR 优化转向以长期用户价值、健康度、留存为目标的偏好对齐。
8. **端到端单模型**：召回、粗排、精排、重排逐步被一个生成模型吸收，简化整个推荐技术栈。

> 一句话总结：生成式推荐正在把推荐系统从"特征工程 + 多级级联的判别式打分"，重塑为"行为序列上的自回归生成 + 可 scale 的基础模型"。如果说 LLM 是文字的 ChatGPT 时刻，那么 GR 可能是推荐系统的 ChatGPT 时刻。
