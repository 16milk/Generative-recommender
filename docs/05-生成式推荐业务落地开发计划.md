# 生成式推荐业务落地开发计划

> 本开发计划基于当前仓库已有文档，结合 Meta `generative-recommenders` 的工程骨架、TIGER 的生成式检索思想、OneRec / OneRec-V2 的 Semantic ID 与偏好对齐路线，给出一套面向业务落地的分阶段建设方案。
>
> 核心建议：**第一阶段以 Semantic ID 生成式召回为核心，参考 Meta `generative-recommenders` 的 `research/` 线跑通序列建模 baseline，参考 OneRec / TIGER 建设 SID Tokenization，通过 `SID -> GID` 倒排把模型生成结果接入现有推荐链路，作为一路可 AB、可监控、可回滚的新召回队列。**
>
> 中长期方向：**在生成式召回稳定贡献增量后，再逐步引入 listwise generation、HSTU 长序列 backbone、Lazy Decoder-Only、reward-weighted SFT / DPO，最终探索召回、排序、重排统一的 one-model 推荐架构。**

---

## 1. 业务落地定位

### 1.1 第一阶段目标

第一阶段不直接替换现有推荐系统，而是在现有推荐链路中新增一路 **Generative Recall（生成式召回）**：

```text
传统推荐主链路保持不变
        │
        ├── 原有召回：双塔 / i2i / 热门 / 规则 / ANN / 其他业务召回
        │
        └── 新增一路：Generative Recall
                  │
                  ├── 用户行为序列建模
                  ├── GR 模型生成 Semantic ID
                  ├── SID -> GID 反查真实物品
                  ├── merge / 去重 / 打散 / 过滤
                  └── 送入原有粗排 / 精排 / 混排
```

第一阶段的业务目标是：

- 在不破坏现有推荐主链路的前提下，验证生成式推荐的增量价值。
- 建设一条完整的 `数据 -> SID -> 模型 -> 检索 -> 服务 -> 监控 -> 反馈` 闭环。
- 形成可复用的生成式召回基础设施。
- 为后续 listwise 生成、偏好对齐、召回排序统一打基础。

### 1.2 不建议第一阶段做的事情

第一阶段不建议直接做：

- 全量替换现有召回系统。
- 直接替换粗排 / 精排。
- 一开始就训练大模型或 MoE。
- 一开始就引入复杂 RL / DPO / GRPO。
- 一开始就建设完整 HSTU 生产级 kernel。
- 一开始就做召回、排序、重排统一的 one-model 架构。

原因是生成式推荐链路较长，涉及数据、SID、模型、索引、服务、监控多个环节。第一阶段的核心不是追求架构完整性，而是尽快跑通可验证、可上线、可回滚的业务闭环。

## 2. 技术路线总览

### 2.1 融合路线

本项目采用以下融合路线：

| 来源 | 借鉴内容 | 在本项目中的定位 |
|---|---|---|
| Meta `generative-recommenders` | `research/` 训练闭环、SASRec / HSTU baseline、长序列建模、生产级 HSTU 工程经验 | 序列建模骨架与工程参考 |
| TIGER | RQ-VAE / Semantic ID / 生成式检索 | 生成式召回基础范式参考 |
| OneRec | RQ-Kmeans、session-wise generation、DPO 偏好对齐 | Semantic ID 与 listwise 生成主线参考 |
| OneRec-V2 | Lazy Decoder-Only、真实用户反馈对齐、GBPO | 后续 scale 与 post-training 参考 |
| 现有业务系统 | 行为日志、item embedding、召回链路、粗排精排、AB 平台、监控平台 | 真实落地载体 |

```text
                    └───────────────┬──────────────┘

│ multimodal / co-watch │   │ RQ-Kmeans / Balanced RQ       │
└──────────────────────┘   └───────────────┬──────────────┘
                                           │
                                           ▼
                    ┌──────────────────────────────┐
                    │        GR Model Training       │
                    │ SASRec / HSTU / EncDec / Lazy  │
                    └───────────────┬──────────────┘
                                    │
                                    ▼
                    ┌──────────────────────────────┐
                    │        GR Serving             │
                    │ Beam SID -> SID2GID -> Merge  │

                    ┌──────────────────────────────┐
                    │   原有粗排 / 精排 / 混排系统     │

                    ┌──────────────────────────────┐
                    │  AB / 监控 / 反馈回流 / 再训练   │
                    └──────────────────────────────┘
```

### 2.3 核心技术选择

| 模块 | 第一阶段选择 | 后续演进 |
|---|---|---|
| Item Tokenization | RQ-Kmeans / Balanced RQ-Kmeans | RQ-VAE、Balanced RQ-VAE、End-to-End Tokenizer |
| 训练样本 | Pointwise `history -> next SID` | Listwise / session-wise generation |
| 模型 baseline | SASRec、Transformer Encoder-Decoder | HSTU、Decoder-heavy、Lazy Decoder-Only、MoE |
| 训练目标 | next-token CE、action-weighted CE | reward-weighted SFT、DPO、GRPO / GBPO |
| 检索方式 | `SID -> GID` 倒排 | ANN fallback、Trie constrained decoding |
| Serving 策略 | beam search + snake merge | 动态 beam、temperature、KV cache、GPU serving |
| 上线方式 | 新增一路召回队列 | 召回增强、listwise rerank、召回排序统一 |

## 3. 阶段一：业务试点与离线最小闭环

### 3.1 目标

跑通最小离线闭环：

```text
行为日志 -> 用户行为序列 -> Item Embedding -> SID -> 模型训练 -> 离线评估
```

这个阶段主要回答以下问题：

- 当前业务的用户行为序列是否具备足够预测性？
- 生成式推荐是否能超过简单序列推荐 baseline？
- Semantic ID 路线是否优于原始 Item ID 路线？
- SID 的均匀度、有效率、反查能力是否满足召回服务化要求？
- 后续是否值得投入线上召回队列建设？

### 3.2 输入资料

需要准备：

```text
uid: 用户 ID
gid / item_id: 物品 ID
action: 行为类型
timestamp: 行为时间
scene: 推荐场景 / 入口
request_id / session_id: 请求或会话 ID，若有
item_embedding: 物品向量
item_side_info: 类目、作者、时长、发布时间、内容特征等
```

### 3.3 数据处理任务

- 清洗用户行为日志。
- 定义正向行为集合，例如 click、play、finish、like、share、download、purchase 等。
- 按 `uid + timestamp` 构建用户行为序列。
- 构建 pointwise 样本：

```text
history_items + history_actions + context -> next_item / next_sid
```

- 按时间切分 train / valid / test，避免数据泄漏。
- 统计用户序列长度、item 热度分布、action 分布、场景分布。

### 3.4 SID Tokenizer 任务

第一版优先使用 RQ-Kmeans 或 Balanced RQ-Kmeans：

```text
item_embedding
  -> 第 1 层 K-means
  -> 残差计算
  -> 第 2 层 K-means
  -> 残差计算
  -> 第 3 层 K-means
  -> gid2sid / sid2gid
```

输出：

```text
gid -> sid path
sid path -> gid list
sid level codebook
sid metrics report
```

SID 评估指标：

- code 利用率。
- Gini / 熵 / 分布均匀度。
- path 覆盖率。
- 平均每个 SID path 挂载 item 数。
- 最大簇 / 热门 path 占比。
- 空 path 比例。
- embedding reconstruction hitrate。
- i2i 语义邻近性。
- 长尾 item 覆盖率。
- 新 item 覆盖率。

### 3.5 模型 baseline 任务

同时建设两条 baseline：

#### Baseline A：Item-ID 序列推荐

参考 Meta `generative-recommenders` 的 `research/` 线：

```text
history item ids -> SASRec / HSTU-style encoder -> next item id
```

作用：

- 验证用户行为序列预测能力。
- 提供可解释的传统序列推荐对照。
- 对齐 Meta 的训练 / 评估范式。

#### Baseline B：Semantic-ID 生成式召回

参考 TIGER / OneRec：

```text
history sid sequence -> Transformer / Encoder-Decoder -> next sid path
sid path -> gid list
```

作用：

- 验证 SID 生成是否可用于召回。
- 评估 SID 对长尾、冷启动、泛化能力的帮助。
- 为线上生成式召回服务做准备。

### 3.6 离线评估任务

模型指标：

```text
HR@K
Recall@K
NDCG@K
MRR
```

召回业务指标：

```text
正反馈 item hitrate
高价值 action hitrate
长尾 item 覆盖率
新 item 覆盖率
多样性
重复率
热门偏置
```

SID 服务化指标：

```text
SID 有效率
SID 空结果率
SID -> GID 反查成功率
平均召回 item 数
```

### 3.7 阶段产物

- 数据 Schema 与样本构造说明。
- `gid -> sid` / `sid -> gid` 映射文件。
- SID 质量评估报告。
- Item-ID baseline 训练与评估报告。
- SID baseline 训练与评估报告。
- 离线模型对比报告。
- 是否进入线上召回服务化的决策结论。

## 4. 阶段二：生成式召回服务化

### 4.1 目标

把 GR 模型作为一路召回队列接入现有推荐系统：

```text
用户请求
  -> 获取用户 profile / long seq / short seq
  -> GR 模型生成 top beam SID path
  -> SID -> GID 倒排反查
  -> 多 SID merge
  -> 去重 / 过滤 / 打散
  -> 返回候选 item
  -> 接入原有粗排 / 精排 / 混排
```

### 4.2 服务模块

需要建设以下模块：

#### 4.2.1 用户序列特征模块

- 获取用户近期行为序列。
- 获取用户长期行为序列。
- 获取用户 profile / context。
- 保证离线训练与在线 serving 的特征口径一致。
- 处理新用户、低活用户、特征缺失用户。

#### 4.2.2 GR 模型推理模块

- 加载训练好的 SID generation 模型。
- 支持 beam search。
- 支持 top-k / temperature 配置。
- 支持模型版本管理。
- 支持灰度和回滚。

#### 4.2.3 SID -> GID 检索模块

第一版优先使用倒排：

```text
sid path -> [gid_1, gid_2, ..., gid_n]
```

能力要求：

- 支持完整 SID path 查询。
- 支持前缀 SID 查询，作为空结果 fallback。
- 支持 item 状态过滤，例如下架、审核、地域、年龄、库存、可见性等。
- 支持索引版本管理。
- 支持增量更新或定期重建。

#### 4.2.4 Merge 与后处理模块

第一版策略：

- 多 SID 之间使用 snake merge。
- 同 SID 内按热度、质量分、时间或已有召回分排序。
- 对返回 item 做去重。
- 接入现有过滤规则。
- 控制 GR 队列召回量。
- 保留召回 trace，便于训练回流和问题排查。

### 4.3 上线策略

推荐上线顺序：

```text
离线 replay
  -> shadow mode，只记录不出结果
  -> 小流量实验
  -> 扩大流量
  -> 稳定后纳入常规召回队列
```

第一版线上策略：

- 作为新增召回，不替换原有召回。
- 控制召回量，例如每次请求只返回少量候选。
- 控制流量比例。
- 设置快速回滚开关。
- 所有 beam、topk、merge、guarantee 参数配置化。

### 4.4 监控指标

活性指标：

```text
GR 请求成功率
模型推理成功率
SID 生成成功率
SID 有效率
SID 空结果率
召回 item 数
```

链路指标：

```text
进入粗排数量
进入精排数量
最终曝光数量
GR 占比
GR 独占占比
GR 被其他召回覆盖比例
```

效果指标：

```text
CTR
播放 / 停留时长
完播率
互动率
转化率
留存
负反馈率
```

效率指标：

```text
模型推理 p50 / p99 / p999
SID 检索 p50 / p99 / p999
整体召回 p50 / p99 / p999
GPU / CPU 利用率
单位请求成本
```

生态指标：

```text
长尾 item 曝光
新 item 曝光
热门集中度
作者 / 类目多样性
重复率
内容安全过滤率
```

### 4.5 阶段产物

- GR recall service。
- SID 倒排索引服务。
- GR 队列 merge 策略。
- 线上特征一致性校验。
- 监控 dashboard。
- shadow / AB 实验报告。
- 线上回滚预案。

## 5. 阶段三：Listwise 生成与长序列 scale

### 5.1 目标

从 pointwise `history -> next SID` 演进到 listwise / session-wise generation：

```text
history + context -> next item list / next SID list
```

该阶段重点提升：

- 召回覆盖。
- 列表多样性。
- session 内 item 之间的互补性。
- 长序列兴趣建模能力。
- 模型 scale 后的离线和线上收益趋势。

### 5.2 Listwise 样本建设

构造样本：

```text
user_profile
long_seq
short_seq
context
target_session_gid_list
target_session_sid_list
action / reward labels
```

关键任务：

- 按 request_id / session_id 组织曝光与反馈。
- 定义高质量 session。
- 对重复训练 item 做 mask。
- 支持同一请求内 item 的 listwise target。
- 对 session 内顺序噪声进行处理。

### 5.3 模型演进

模型从简单 baseline 演进为：

```text
Encoder-Decoder SID baseline
  -> Decoder-heavy
  -> HSTU backbone
  -> Lazy Decoder-Only
  -> MoE / Sparse FFN
```

演进原则：

- 先保证训练和推理一致。
- 先做可解释的模型消融，再引入复杂结构。
- 先扩大序列长度，再扩大模型规模。
- 先观察离线 scale trend，再投入线上大流量。

### 5.4 Serving 演进

服务能力增强：

- 更大 beam size。
- beam 预截断。
- 金字塔 beam。
- KV cache。
- GPU serving。
- BF16 / FP16 / INT8。
- 动态 beam / temperature / topk。
- Trie constrained decoding。

### 5.5 阶段产物

- Listwise 样本构造文档。
- Listwise 模型训练任务。
- Session-wise 生成评估报告。
- 长序列建模消融报告。
- HSTU / Decoder-heavy / Lazy Decoder 对比报告。
- Serving 性能优化报告。

## 6. 阶段四：业务 Reward 与偏好对齐

### 6.1 目标

在生成式召回稳定后，引入业务 reward，使模型从“生成可能相关的 item”进一步演进为“生成更符合业务目标的 item list”。

### 6.2 Reward 设计

需要定义多目标 reward：

```text
click reward
play / stay time reward
finish reward
like / share / comment reward
download / purchase reward
retention reward
negative feedback penalty
diversity reward
valid SID reward
```

注意事项：

- 观看时长类 reward 需要去除内容长度偏置。
- 互动类 reward 需要防止标题党和低质内容放大。
- 商业化 reward 需要设置用户体验护栏。
- 多样性和冷启动要作为生态护栏指标。

### 6.3 训练方式演进

推荐顺序：

```text
next-token CE
  -> action-weighted CE
  -> reward-weighted SFT
  -> chosen / rejected 样本构造
  -> DPO / Listwise DPO
  -> GRPO / GBPO
```

### 6.4 偏好样本构造

可以从以下来源构造 chosen / rejected：

- 线上曝光后真实用户反馈。
- 同一请求内高互动 item vs 低互动 item。
- beam 生成候选经 reward model 打分后的 top / bottom。
- 精排模型或多目标模型打分。
- 人工标注或内容质量分。
- 显式负反馈，例如 dislike、不感兴趣、举报、快速划走。

### 6.5 阶段产物

- Reward 定义文档。
- Reward-weighted SFT 训练任务。
- DPO / Listwise DPO 样本构造任务。
- Reward model 或 teacher score 接入方案。
- 偏好对齐实验报告。
- 多目标指标与护栏指标报告。

## 7. 阶段五：召回、排序、重排统一探索

### 7.1 目标

在 GR 召回队列稳定贡献业务增量后，探索更统一的推荐模型：

```text
GR recall
  -> GR recall + rank
  -> listwise rerank
  -> one-model recommendation
```

### 7.2 探索方向

- 用 GR 模型输出作为粗排特征。
- 用 GR 模型生成候选 list 后进行 listwise rerank。
- 在生成过程中引入排序目标。
- 在 decoder 上增加多任务 head。
- 统一建模召回目标与排序目标。
- 通过 post-training 对齐最终业务目标。

### 7.3 风险控制

- 不直接替换现有精排主模型。
- 先做旁路打分和离线 replay。
- 再做小流量 AB。
- 始终保留原链路兜底。
- 设置业务护栏指标。

### 7.4 阶段产物

- GR rank feature 接入方案。
- Listwise rerank 实验报告。
- 多任务生成模型设计文档。
- one-model 推荐长期路线图。

- 生态指标监控。
- 延迟和成本监控。

## 9. 风险与治理

### 9.1 数据风险

- 行为日志质量不足。
- 用户序列过短。
- 训练 / serving 特征不一致。
- 时间切分不严格导致数据泄漏。
- 流式样本重复训练。

治理方式：

- 建立数据校验。
- 固定时间切分协议。
- 建设离线 / 在线特征一致性检查。
- 对重复样本做 mask。

### 9.2 SID 风险

- codebook collapse。
- SID 分布极度不均。
- path 过热或过稀。
- SID -> GID 空结果率高。
- 新 item SID 更新不及时。

治理方式：

- 监控 code 利用率、Gini、path 覆盖率。
- 引入 Balanced RQ-Kmeans。
- 建设 prefix fallback。
- 建设 SID 版本管理与增量更新。

### 9.3 模型风险

- 生成重复 item。
- 放大热门偏置。
- 长尾和冷启动曝光下降。
- 离线指标和线上指标不一致。
- 模型生成有效 SID 但业务价值不足。

治理方式：

- 增加 diversity / de-dup 指标。
- 监控长尾和新 item 曝光。
- 引入 reward-weighted SFT。
- 保留现有召回兜底。

### 9.4 Serving 风险

- beam search 延迟过高。
- SID 检索空结果率高。
- 索引版本与模型版本不一致。
- GR 队列挤压原有高效队列。

治理方式：

- 使用小 beam 起步。
- 所有参数配置化。
- 模型与 SID 索引版本绑定。
- 设定 GR 队列召回上限和保送上限。

## 11. 最终路线总结

本项目的业务落地路线可以总结为：

```text
第一阶段：Semantic ID 生成式召回
  -> 基于 Meta research 线跑通序列建模 baseline
  -> 基于 TIGER / OneRec 建设 SID Tokenizer
  -> 通过 SID->GID 倒排接入现有推荐系统
  -> 作为一路可 AB、可监控、可回滚的新召回队列

第二阶段：Listwise + 长序列 scale
  -> 从 next-item / next-SID 演进到 next-list / session-wise generation
  -> 引入 HSTU、Decoder-heavy、Lazy Decoder-Only
  -> 提升召回覆盖、多样性、长尾和业务效率

第三阶段：业务 Reward 与偏好对齐
  -> reward-weighted SFT
  -> DPO / Listwise DPO
  -> 真实用户反馈对齐
  -> 优化 pass@1 和多目标业务指标

第四阶段：召回、排序、重排统一探索
  -> GR recall + rank
  -> listwise rerank
  -> one-model recommendation
```

最重要的原则是：**先闭环，再 scale；先召回，再统一；先 SFT，再对齐；先可控上线，再追求架构终局。**
